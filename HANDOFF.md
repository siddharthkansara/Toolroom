## What it is
A shop-floor web app (installable PWA) for a precision cold-forging bearing-roller business. Three factories (NIC, PEW, BABA) order tooling (dies, bottoms, forging punches, forging pins) from ONE shared CNC lathe 10 km away. Tools are machined at the CNC, then travel back to the plants. The app tracks: orders, the CNC queue and batches, tooling INVENTORY per factory, the SHIFT SHEET (production per header per shift, now entered by WEIGHT with batch and heat numbers), and an owner DASHBOARD.
Owner: Siddharth (not a developer). He copy-pastes into VS Code and the Supabase SQL Editor, tests on an Android phone, and deploys by `git push` to GitHub -> Vercel. **On 7 Nov 2026 he reported that everything built so far is pushed to git and working fine.** Keep the habit: push after each confirmed phase.
Long-term goal: feed a whole order schedule (roller size + quantity) and get the tooling needed (the Tool Plan does this), and automate more. Keep data clean with that in mind.

## How to work with him (important)
- Token budget is tight: small targeted snippets or patches. For bigger code, create files and present them (always call `present_files`; he once could not find a file because it was created but not presented). Do NOT rewrite whole existing files unless asked. Exception that worked well: when I authored a file myself (e.g. `dashToday.tsx`) and 5 places change, hand over the whole file.
- For big features: share a plan first (with the assumptions listed), then work in phases and stop for confirmation ("start phase N"). He often says "continue" after a cut-off: carry on, do not restart.
- Shop users have low digital literacy: big tap targets, minimal typing, English only, field labels ALWAYS visible above inputs, uncluttered lists, one view per button, confirmations that fade after a few seconds. Owner wants the dashboard minimalist, uncrowded, "looks smaller, not smaller in size".
- Times shown in IST. He runs `npm run build` and pastes errors; VS Code also shows TypeScript errors.
- Be honest about what is untested. The assistant cannot run his app, Supabase or `npm run build`; there is no Postgres or node_modules in the sandbox. What CAN be done and was done each time: `tsc` parse check on a scratch copy (`--ignoreDeprecations 6.0`, add minimal React type stubs to catch undefined names), and logic tests of components with stubbed React/supabase in plain node. Say clearly "SQL untested, test script provided".
- Database test scripts are self-rolling-back `do $$ ... raise exception 'TEST PASSED AND ROLLED BACK ...' $$` blocks. Newer ones pick an owner, a toolroom user and a roller by themselves (no placeholders to paste). Success = that exact error message.
- The assistant cannot send reminders; he must set his own.
- Mistakes to avoid (all happened):
  1. Module-level `const` helpers declared BELOW the component cause "before initialization".
  2. Never put a freshly built array (e.g. `orders`) in a `useEffect` dependency list; use stable state or primitives (strings/numbers).
  3. New tables/views must be added to the `Database` block in `types/database.ts` (hand him the WHOLE block). Trick used since: expose new data through RPC functions and local `rpcData<T>()` instead, so the Database block is untouched. Plain row types (e.g. `ShiftEntry`) are edited on their one line.
  4. The global `JSX` namespace is not available (use `ReactElement`).
  5. `cut -c` or byte slicing on lines with emoji corrupts text (and can crash terminal output); use Python.
  6. An instruction to "change a line" must keep every statement on that line.
  7. **Markdown tables eat backticks.** Never put template literals (`` `${...}` ``) inside a markdown table; it produced 6 broken `className` edits. Put all code in fenced blocks, and prefer string concatenation in tiny edits.
  8. **Very long single-line replacements are fragile for him.** Replace a whole function/block instead (e.g. the whole `ShiftSheet` function), or give exact anchor text. Never rely on his line numbers; he edits files himself. When his build errors persist, ask him to paste the specific lines as text, or upload the current file and diff it against what was intended (this found a deleted roller-size label).
  9. Tell him when a migration changes behaviour for live users (e.g. migration 29 refuses lines without weight/batch/heat): run SQL and push the matching code together, at a quiet time.
  10. `now()` is constant inside a transaction. Anything ordered by time must use `clock_timestamp()` (fixed in `roller_rate_history`).
  11. Old zips lack migrations 02-15 and 21 and had a stale nested `roller-pwa/` folder. Always ask for a fresh zip.

## Stack
Next.js 16 App Router + TypeScript, Tailwind v3, Supabase (Postgres, Auth, Realtime, PostgREST 12), Vercel. `tailwind.config.ts` must scan BOTH `./app/**` and `./lib/**`. Row types in `types/database.ts` (use `type`, not `interface`). `lib/supabase.ts` exports `supabase` and `rpc(fn, args)` (returns only `{error}`); screens that need returned data use a local `rpcData<T>()` helper that casts `supabase.rpc`.

## Theme
Light theme is a CSS override block at the end of `app/globals.css`, keyed on `<html data-theme="light">` (toggle in `lib/theme.tsx`). ## Shift sheet (big changes this round)
One line = one header running one roller size in one shift. `shift_entries(factory_id, work_date, shift DAY|NIGHT, machine_id, status RAN|NOT_RUNNING, roller_id, operator_id, rollers_forged, weight_kg, note, short jsonb, soft-delete cols, rollers_per_kg, batch_no, heat_no)`, `shift_tools`, `shift_sheets`, `header_operators`, `shift_settings`, views `shift_entries_live` (recreated in migration 29), `shift_totals`. Shifts: DAY 7:30-19:30, NIGHT 19:30-07:30 (belongs to the date it started). Entry windows: day until 7:30 pm same day, night until 11:49 am next day; after that only the owner edits. Nothing before a shift starts.
- **Entry is by WEIGHT.** The operator types only the weight (kg) of rollers forged (assumed to be the TOTAL kg of the line, not per roller; the owner proceeded on this basis, confirm if in doubt). The database computes `rollers_forged = round(weight x rollers_per_kg)`. The form shows the calculated number read-only ("8,250 rollers at 82.5 per kg"). Users cannot type a roller count.
- **Rollers per kg** lives in `roller_rate_history(id, roller_id, rollers_per_kg numeric(12,4) >0, set_by, set_at default clock_timestamp())`, a history ledger, one rate per roller size, OWNER ONLY (migration 28). RPCs: `roller_rates_list(p_factory)` (all sizes with current rate, null = not set), `roller_rate_history_of(p_roller)` (last 20), `set_roller_rates(p_rows jsonb [{roller_id, rate}])` (owner only, refuses <=0 or >100000, skips unchanged, returns count). UI: owner-only button "Rollers per kg" in the Shift Sheet tab (`lib/rollerRates.tsx`): factory chips, search, "Not set yet (N)" filter (unset first), current rate + date, bulk Save, History, confirm when a rate moves more than 25%. A size with no rate cannot be entered.
- **`shift_entry_save`** (migration 29, 14 params: `p_id, p_factory, p_date, p_shift, p_machine, p_status, p_roller, p_operator, p_rollers (accepted but IGNORED), p_tools, p_note, p_weight, p_batch, p_heat`; returns `{id, short}`): RAN lines require weight > 0, batch no., heat no., and a rate; weight x rate over 100,000,000 is refused; batch/heat are trimmed, upper-cased, max 40 chars. **The rate used is stored on the line** (`rollers_per_kg`); editing a line keeps its original rate if the roller size is unchanged, a new line (or changed size) uses the owner's current rate, so a rate change never alters past production. ## Appendix: SQL for migrations 26/27 (in case the files were never saved)
Migration 27 (also contains everything migration 26 did; run it if 26 was never run):
```sql
alter table tool_orders add column if not exists priority_was priority_enum;
alter table tool_orders add column if not exists priority_changed_at timestamptz;

create or replace function public.order_set_priority(p_ids uuid[], p_priority priority_enum)
returns integer language plpgsql security definer set search_path = public as $$
declare n integer;
begin
  if p_priority::text not in ('URGENT', 'URGENT_MACHINE_DOWN') then
    raise exception 'Priority can only be raised to Urgent or Breakdown';
  end if;
  update tool_orders o set priority_was = o.priority, priority_changed_at = now(), priority = p_priority
   where o.id = any(p_ids) and o.status = 'QUEUED' and can_write(o.factory_id)
     and (case o.priority::text when 'BUFFER_NEXT_SHIFT' then 2 when 'URGENT' then 1 else 0 end)
       > (case p_priority::text when 'URGENT' then 1 else 0 end);
  get diagnostics n = row_count;
  if n = 0 then
    raise exception 'Nothing changed: the tool may already be on the lathe, or already at this priority or higher.';
  end if;
  return n;
end $$;
grant execute on function public.order_set_priority(uuid[], priority_enum) to authenticated;
```
Before running, check the priority values in the live database: `select enum_range(null::priority_enum);` should list URGENT_MACHINE_DOWN, BUFFER_NEXT_SHIFT and URGENT (migration 01 only had two).
